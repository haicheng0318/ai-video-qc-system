## 范围与门禁

本地测试使用专用 PostgreSQL、人工构造数据、替换模型传输的夹具、本机 HTTP 对象服务器和 Chromium。该本地证据没有调用真实 COS/OSS 或付费模型。2026-09-11 的生产发布证据单独记录于下方；没有推送代码、创建真实账号或运行空库初始化。

本地旧库演练以已完成前 7 个迁移的 V1.0 schema 为起点，覆盖全部 12 张核心表、返修关联、独立三级结果、原始响应、人工确认与审计。它不是生产备份，也不代表所有历史数据形态。更早版本迁移含“规则/最终表应为空”的前提，必须在真实基线核验后另行处理；不得直接清空表来满足迁移。

生产发布仍有这些独立门禁：

- 批准具体目标、维护起止时间、负责人、备份保留及恢复目标、会话强制重新登录和验证/回退方案。
- 取得只读基线：当前镜像摘要、源码候选、已应用迁移及失败迁移、运行服务、worker 数量、数据库版本和行数、对象存储类型/前缀/TTL。历史健康响应不能证明源码版本。
- 真实 COS 的私有 ACL、PUT 大小/类型签名、CORS、HEAD、条件复制、同票据重放、Range、过期/续签与清理；OSS 临时对象上传/失败清理及生命周期。演练对象服务器不冒充 COS。
- 付费样本的阶段、数量、模型、单次最长时限、总预算、重试边界以及调用后不确定费用处置。费用未观察时保持未知，不能记成 0 元。
- 依赖门禁已于 2026-09-10 关闭：生产 npm 已知告警 19→0，完整兼容验证及独立安全复审通过。发布时仍须按当时漏洞库重扫实际候选，并单独核对基础镜像/OS。
- 候选独立代码审查，以及生产小范围试运行记录。WebKit/Firefox、真实移动设备、云资源/证书/账单采集均不属于本轮已验证证据。

## 本地启动与隔离测试

普通开发见根 README。V1.01 需要分别启动 API、Web 和独立 worker；不启动 worker 时新评估保持排队。所有模型/云密钥只置于后端。

```sh
npm install
npm run db:generate
npm run build:shared
npm run dev:api
npm run dev:web
npm --workspace @ai-video-qc/api run worker:dev
```

真实开发库的迁移/初始化只在选定目标后显式进行；以下专门用于安全验收，拒绝默认项目数据库：

```sh
node --test deploy/lighthouse/tests/*.spec.mjs
QC_LOCAL_REHEARSAL=1 node deploy/lighthouse/local-release.mjs rehearse
QC_LOCAL_REHEARSAL=1 node deploy/lighthouse/local-release.mjs prepare-tests
QC_LOCAL_REHEARSAL=1 node deploy/lighthouse/verify-local.mjs
QC_LOCAL_REHEARSAL=1 node deploy/lighthouse/local-image-smoke.mjs
QC_LOCAL_REHEARSAL=1 node deploy/lighthouse/local-source-audit.mjs
```

`rehearse` 使用新的库名依次执行：空库全部迁移、七迁移代表性存量、12 核心表旧字段逐行指纹对照、迁移前自定义格式备份、恢复到新库再向前迁移、切换后新增审计的再次备份恢复、12 迁移与 schema drift 核对。输出保留于工作台账 `task5-release/<run>/`，含备份 SHA-256、行数/指纹及迁移日志。不会执行 `DROP DATABASE`、`migrate reset`、`pg_restore --clean` 或覆盖已有恢复目标。

`prepare-tests` 仅首次创建四个专库 `release_test`、`identity_test`、`queue_test`、`ops_test`，均位于 `127.0.0.1:55441`，角色与库同名，口令仅为 `task5-local-only`（人工测试夹具，不可用于部署）。已存在时拒绝重建。此后直接复跑：

推荐直接使用 `verify-local.mjs`：它清理子进程继承环境，依次保存发布保护测试、API 编译、四个历史阶段HTTP脚本、全部 API/Web 测试、类型、生产构建、diff 检查和只读依赖扫描。阶段脚本在导入任何应用模块前先验证/设置隔离环境，避免签发与校验JWT使用不同初始化配置。依赖扫描非零被单独保留，不能当作安全通过。以下是测试变量对照，不应附带真实模型或云密钥：

```sh
QC_SKIP_DOTENV=1 JWT_SECRET=local-test-only-secret-at-least-32-characters \
QC_LOCAL_ACCEPTANCE=1 \
IDENTITY_TEST_DATABASE_URL=postgresql://identity_test:task5-local-only@127.0.0.1:55441/identity_test \
EVALUATION_JOBS_TEST_DATABASE_URL=postgresql://queue_test:task5-local-only@127.0.0.1:55441/queue_test \
OPS_TEST_DATABASE_URL=postgresql://ops_test:task5-local-only@127.0.0.1:55441/ops_test \
RELEASE_TEST_DATABASE_URL=postgresql://release_test:task5-local-only@127.0.0.1:55441/release_test npm test
npm run typecheck
npm run build
```

没有提供专库变量的普通 `npm test` 会跳过 opt-in 数据库测试，不能据此声称数据库/HTTP 全部通过。历史四个 `test:http:*` 脚本现在要求 `QC_LOCAL_ACCEPTANCE=1` 和 `HTTP_ACCEPTANCE_DATABASE_URL`，默认拒绝执行；新全链路脚本覆盖真实 API、持久队列和独立进程故障，应作为本轮主证据。

浏览器先启动本机 Web（同源空 API 基址，脚本会模拟 API 并拦截外部网络）：

```sh
NEXT_PUBLIC_API_BASE_URL='' NEXT_PUBLIC_VIDEO_UPLOAD_MODE=multipart NEXT_TELEMETRY_DISABLED=1 \
npm --workspace @ai-video-qc/web run dev -- -p 3107
QC_LOCAL_REHEARSAL=1 BROWSER_BASE_URL=http://127.0.0.1:3107 node apps/web/scripts/v101-browser-acceptance.mjs
QC_LOCAL_REHEARSAL=1 OPS_BROWSER_BASE_URL=http://127.0.0.1:3107 node apps/web/scripts/admin-operations-browser-acceptance.mjs
QC_LOCAL_REHEARSAL=1 OPS_BROWSER_BASE_URL=http://127.0.0.1:3107 node apps/web/scripts/admin-settings-concurrency-browser.mjs
QC_LOCAL_REHEARSAL=1 RELEASE_BROWSER_BASE_URL=http://127.0.0.1:3107 node apps/web/scripts/release-browser-acceptance.mjs
```

四个直接入口均先要求 `QC_LOCAL_REHEARSAL=1`，拒绝 `NODE_ENV=production`、远端、非 HTTP(S)、URL 内用户名/口令；拒绝发生在查找工具、创建截图目录、启动浏览器或开发服务器之前。它们给工具、Chromium 和自动启动的开发服务器只传递最小环境，不继承模型/云密钥、数据库地址、代理或 `NODE_OPTIONS`。对生产构建执行浏览器验收时，验收进程仍不能设置 `NODE_ENV=production`；已启动的本地被测 Web 可以是生产构建。

发布验收应再对已构建 Web 的本机 `next start` 运行同样脚本。新增浏览器脚本使用真实可播放 WebM、两次失败的只读查询、保留播放器/草稿、一次续签恢复和 1440/390 视口；媒体 error 事件为注入，TTL 另由真实本机 HTTP 夹具验证。不会触发真实模型。

`local-image-smoke.mjs` 构建不推送的唯一标签 API/Web 镜像，立即解析并登记不可变的完整 image ID，实际渲染 Lighthouse Compose 并验证四个 API 角色引用一致、Web 单独引用、没有 build/pull。之后消费该模板解析出的 image ID，在新空库显式迁移；迁移容器退出 0 且实际 Image 与登记一致才允许启动 API，API 实际 Image 一致且运行中才允许启动 worker，再启动 Web。`release-candidate.json` 与 `startup-image-checks.json` 保存检查证据；负向测试验证镜像分离或迁移失败时启动动作不会执行。随后执行四组 Chromium 和图片优化入口 HTTP 验证。应用只连接带本地标签的 internal Docker 网络；Docker Desktop 不发布 internal 网络的端口，因此一个无凭据、固定两个目标的本机转发容器提供 `127.0.0.1:3141/3107`，应用容器本身仍无外网路由。测试结束只停止本次新建服务容器，库/镜像/日志保留，不清理已有资源。镜像构建只可能访问公开软件包仓库，不带云/模型密钥。

`local-source-audit.mjs` 将选定源码文本和本次客户端静态产物复制到新临时目录，用本机已缓存 Gitleaks 镜像断网扫描并输出脱敏结果及逐文件 SHA-256；不读取 dotenv/历史/媒体/压缩归档。浏览器复跑使用独立 `task5-browser/<run>/<stage>/` 目录，不覆盖 Task3/Task4 原始验收截图。所有辅助脚本没有生产模式；执行前还需具备本机已安装 Node/npm、Playwright Chromium 和已缓存 Docker 基础/扫描镜像。

## 维护窗口与部署顺序

1. 在维护开始前只构建一次候选 API 镜像，单独构建同源 API 基址和 multipart 配置的 Web 镜像。构建/载入/获准后的拉取与发布消费分开。登记源码清单、两个镜像摘要及目标主机解析出的 image ID，设置 `API_IMAGE`、`WEB_IMAGE` 为已登记的 `仓库@sha256:完整64位摘要` 或该主机 `sha256:完整64位image ID`，拒绝 latest/版本标签/短 ID。Compose 的 API、worker、migrate、bootstrap 共享 `API_IMAGE`，Web 使用独立 `WEB_IMAGE`，缺任一引用即拒绝解析；模板没有 build 且 pull_policy=never，发布不得使用 `--build` 或另行给角色构建服务标签。准备保持 Cookie/会话与当前数据库兼容的修复镜像。生产窗口长度不能由本地秒级演练推算，应包含真实备份、恢复演练、验证与回退余量。
2. 维护入口暂停新上传、业务写入与评估触发。等待正在执行的 worker 完成并停止旧 worker；不得同时运行旧内存任务 API 和新持久 worker。明确等待上限，调用后未知结果应记录为人工处理，不自动重发。
3. 在写入静止后，保存数据库自定义格式备份、校验和、核心表行数、迁移状态，以及本地视频/封面卷快照与对象版本清单。数据库备份不包含 COS、OSS 或本地媒体。备份恢复到独立库验证，原库和原媒体保持可恢复。
4. 先只读解析所有 profile 的 `config --format json`，核对四个 API 角色的 image 完全等于登记的不可变引用、Web 等于独立引用且无 build/pull；用 `docker image inspect <已登记引用> --format '{{.Id}}'` 记录实际 API ID。任何引用缺失、可变、未载入或不一致均停止。对已核准目标显式运行候选镜像的 `migrate` profile；命令模板为 `docker compose ... --profile maintenance run --no-deps --name <本次唯一迁移容器名> migrate`，数据库应已健康。不要加 `--rm`，须保留该容器用于下一步检查；真实 `.env`、主机和项目名须人工核准。任何失败停止发布，检查迁移状态，不清库、不盲目 `migrate resolve`。
5. **API 启动前门禁**：只读检查 `docker inspect <本次迁移容器名> --format '{{.Image}} {{.State.Status}} {{.State.ExitCode}} {{.State.OOMKilled}}'`，必须与第 4 步登记的 API ID 完全相同且为 `exited 0 false`，保留输出。通过后才以 `up -d --no-build --no-deps api` 启动候选 API。使用 `/api/health/live` 和 `/api/health/ready` 验证进程/数据库；验证 Cookie 登录、CSRF、旧 Bearer 拒绝、用户角色与访客到期、受控播放。所有用户需重新登录，旧 localStorage Token 不迁移。
6. **worker 启动前门禁**：用已核准 Compose 项目 `ps -q api` 取得确切 API 容器，读取 `docker inspect <API容器ID> --format '{{.Image}} {{.State.Running}}'`，必须与登记的 API ID 完全相同且为 `true`，保留输出；仍需保留已成功的同镜像迁移证据。通过后才以 `up -d --no-build --no-deps worker` 启动 worker，检查独立心跳、队列领取和异常分类；再以同样禁 build 的方式切换新版 Web，验证三个环节按 ID 同步。迁移与 API 验证未完成不得把新版 Web 暴露给业务用户。
7. 按已批准样本/预算进行真实云与模型小范围验收，再逐步恢复写入。记录样本视频、三级结果、来源、确认人、失败/用量/对象清理证据。达到失败阈值立即重新进入维护。
8. 仅空库初始化才单独运行 `bootstrap` profile；它会创建管理员并写模型配置，升级已有环境不运行。正常 API 重启只启动服务，不执行迁移或 seed。

上述步骤仍是以后发布/回退的标准检查单。本地演练程序通过同一纯校验模块 `release-image-contract.mjs` 自动拒绝可变引用/分离镜像，并在实际启动动作之前完成容器比对；它仍默认拒绝生产和远端。不要以改 opt-in 变量的方式把本地演练程序用于生产。

## 回退与向前恢复

优先停止业务写入与 worker，保留当前数据库、队列/attempt、额度账本、AI 原始返回、审计及新增媒体；切换与当前 schema 和 Cookie 会话兼容的已验证镜像。不能直接用 V1.0 Bearer/API 内存任务镜像接管，否则会重新引入认证绕过和重复调用风险。

若需恢复数据库：先为故障现场再做备份，恢复到全新目标库，核对 12 核心表、关联、会话/配额、已确认结论、迁移与媒体对象一致性；把恢复库向前升级到当前 schema。存在切换后新增记录时必须保留/重放到新库并验证，未实现重放时不能声称零数据丢失。切换连接需要再次授权；演练只证明新库恢复和新增审计保留，不证明生产 RPO/RTO。
