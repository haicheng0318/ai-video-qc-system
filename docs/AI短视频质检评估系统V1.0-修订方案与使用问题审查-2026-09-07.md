# AI短视频质检评估系统 V1.0：修订开发方案与使用问题审查

报告日期：2026-09-07  
文档修订：2.0（不是将产品升级为 V2.0）  
交付性质：代码审查与开发方案；本次未修改业务代码、生产配置、账号或密钥。  
本报告汇总并修订此前的完整改造方案，作为下一轮开发的范围基线。

## 一、结论与推荐路线

建议采用“保留业务内核，先补可靠性，再完成前台与独立管理后台”的方案。不推倒重建，不与视频需求数据看板合并代码、数据库、服务或部署。

本次范围完整包含：播放器与详情布局、参照需求看板的 UI 和交互、独立管理员页面、访客账号及额度、任务中心、服务与存储状态、用量和费用、日志与安全，以及评估结果自动更新。全部纳入开发，但按可验收批次落地。

新增审查发现表明，主要问题不仅是界面：

1. 内容评估完成后缺少持续查询，确实会要求用户刷新。
2. 三个 AI 环节依赖 API 进程内后台执行，缺少持久化任务执行与自动恢复机制。
3. 长时间停留后，签名播放地址没有续签处理。
4. 登录失败和登录过期采用同一种 401 跳转处理，体验不合理。
5. 看板存在北京时间边界与日期筛选口径不清的问题。
6. 当前健康接口只证明 API 可以响应，不能证明数据库、模型、存储和完整评估流程可用。

不应以“健康接口正常”“测试通过”或“页面能打开”作为整个系统完成验收的依据。

### 已具备、应继续保留的能力

- 后端并非没有权限控制：按用户与角色检查资源可见性；登录已有限流。
- JWT 校验会查询当前启用用户。停用账号可阻止后续 API 请求，角色也不是只信任旧 Token 中的值。
- 内容评估完成/失败写入前会检查该评估仍为 running。不能把“旧任务必定覆盖新任务”列为现成缺陷；新任务系统需保留并增强这层保护。
- 数据复盘和最终建议已有轮询，不需要从零重写所有评估界面。
- 规则引擎、负责人确认、历史评估及操作日志已存在，改造不得削弱这些边界。

### 需要验证、不能直接判为漏洞的项目

1. 生产签名视频在弱网、切后台、过期后 seek 的表现；CORS、Range、播放器错误事件。
2. 服务器真实 CPU、内存、磁盘、并发模型调用和大文件临时副本的峰值。
3. 上传文件的内容真实性、损坏检测、时长/分辨率/编码兼容性，以及直传完成核验；不能只依赖扩展名或浏览器 MIME。
4. 刷新、返回、多标签页、重复点击是否产生重复视频或重复付费调用。
5. 运营/投放当前可见范围较大，是否符合实际团队授权；不擅自判定为越权漏洞。
6. HTTPS 证书续期、数据库备份和恢复演练是否持续有效；历史成功不代表长期保障。
7. 历史记录聚合是否需要按视频/返修链去重；需真实多版本样本验证，不能先宣称统计已重复。

## 四、业务范围与不可变边界

继续保留“提交 → 内容质量评估 → 主管初审/返修 → 运营或投放数据 → 数据复盘 → 后端规则 → 最终建议 → 负责人确认 → 案例沉淀”。

- 内容质量、数据表现、最终有效三个等级独立存储、独立展示。
- 沿用已批准接入的千问；内容理解、数据复盘、最终建议依然是三个独立职责，不混成一次打分。
- 数据不足进入 pending_data；不能直接判无效。ROI 低不能直接归因编导。
- AI 给出建议，负责人确认业务结果。管理员管理账号不等于可以跳过最终确认与审计。
- 保留全部12张核心表；每次重试、新数据复盘、规则与最终建议保留来源版本和历史，不覆盖旧结果。
- 不新增自动投放、自动剪辑、自动抓取外部运营数据或自动计算绩效工资。

## 五、前台 UI 与交互方案

### 5.1 视觉统一，系统独立

从视频需求数据看板提取颜色、字体层级、间距、导航、表格、筛选、弹窗、状态标签和移动端行为，形成质检系统自己的 design tokens 与组件规范。先制作登录、列表、详情、管理员首页四个代表页面，再应用全站。

采用左侧导航＋内容区，移动端折叠导航；浅色卡片化布局以可读性为先。统一加载、空数据、无权限、失败和成功状态；颜色之外同时提供文字/图标。不仅“换色”，还统一筛选、返回与表单操作习惯。

前台导航：工作台、视频列表、上传评估、业务看板、优秀案例、反面案例、按权限开放的基准配置、返回需求系统入口。保留筛选/分页到 URL，详情返回列表不丢查询条件。

### 5.2 视频详情

- 桌面首屏为“受限高度播放器＋摘要与下一步”，下方为评估与业务记录。
- 播放器按实际宽高比 contain 展示，不裁切、不拉伸；高度预算建议不超过视口约60%，并设置桌面上限560px。9:16视频在560px高时自然宽度约315px，不再同时硬设360～420px宽造成矛盾。
- 小屏改为纵向排列；横屏视频服从可用宽度与高度预算。提供全屏/放大查看，不让正常浏览被播放器占满。
- 摘要独立显示三个等级、当前状态、负责人/待处理角色、评估更新时间和当前版本；尚无数据显示“待生成/待确认”，不用0分代替。
- 标签页：内容评估、主管审核、运营/投放数据、数据复盘、规则与最终建议、负责人确认、版本历史、操作记录。
- 下一步按钮按角色与服务端 allowedActions 显示；不可操作时解释缺什么、由谁处理。
- 支持返修版本对照与时间戳定位；模型没有可靠时间戳时不伪造跳转。
- 自动同步只更新结果区，不能重建播放器、清空未提交表单或跳回默认标签页。表单离开提醒与草稿保存要考虑账号隔离，敏感数据不长期保存在共享浏览器。

### 5.3 上传与结果体验

- 提交前展示支持格式、文件大小限制和已选文件元数据；对损坏或不支持编码提供可执行提示。
- 区分上传进度、文件校验、已提交、排队、评估，不展示虚构的 AI 百分比。
- 网络异常保留已填写元数据；提供重新选择文件/重试入口，不能静默创建重复记录。
- 异步结果显示问题、证据、建议及来源版本；业务状态和“前端暂时断线”分开。
- 导出报告按当前用户权限生成，记录导出动作；不包含密钥、原始内部错误或长效视频直链。

## 六、评估自动更新与任务可靠性

### 6.1 首批修复：不再手动刷新

触发接口返回 reviewId/jobId 后，前端跟踪该任务而不是无条件追逐 latest。首次进入页面若存在进行中任务也自动恢复查询。

- 前台可见时约3秒查询一次；隐藏时降频，重新激活立即同步。
- 一次请求结束后再安排下一次，避免重叠请求；切换视频时中止旧请求并丢弃过期响应。
- 成功/失败停止轮询，刷新视频状态、对应评估、步骤与可用操作；不要每次轮询拉取整页所有面板。
- 连续网络错误或达到前台等待上限，显示“暂停自动查询/重新连接”。不得把前台等待超时写成后台业务失败。
- 已在执行时按钮不可重复提交，后端仍需幂等与事务保护。查询/刷新不应触发付费重评。
- 兼容旧接口与历史 running 记录，先交付修复，再无缝迁移到统一任务接口。

### 6.2 执行层：持久化任务＋独立 worker

建议复用 PostgreSQL 保存任务并用独立 worker 执行，降低当前小规格部署额外引入队列服务的资源负担。任务执行器独立封装，将来需要专用队列时可替换。新增 worker 是部署变化，不是更换 Next.js/NestJS/PostgreSQL 技术栈。

关键设计：

1. 创建评估记录、任务和额度预占在一个数据库事务中完成，API只负责入队与查询。
2. worker 通过数据库行锁领取任务，设置租约、心跳、attempt、输入版本；全局并发先设1，再根据实测调整。
3. 服务重启后重新发现待执行/租约过期任务，不依赖用户点击触发来回收。
4. 重试必须有错误分类、上限、退避和审计。鉴权/配置错误不自动死循环；返回不确定时先记录与核查，不承诺外部调用严格只计费一次。
5. 提交结果必须匹配有效租约和当前任务版本，防止过期 worker 改写现态。历史模型结果追加保存。
6. 数据复盘绑定指标快照，最终建议绑定内容评估、复盘和规则结果。输入变更后旧建议标为非当前，不能继续确认。
7. 管理员回收/重试需原因和二次确认。外部请求发出后取消不保证能停止供应商计费；UI必须说明。
8. OSS临时文件成功/失败后主动清理，生命周期作为兜底。超过临时文件保留期的重试从COS重新生成中转文件。

### 7.1 访客账号默认方案

访客是具备有限操作权的试用账号，不是匿名访问，也不是仅只读。

- 管理员创建；禁止公开自助注册；初始凭据通过受控渠道交付，首次登录强制改密。
- 可登录、改密、上传、评估自己的视频、查看自己的历史与报告、查看额度和到期时间。
- 默认不能访问他人视频、全局看板和非授权案例，不能填正式运营数据、主管初审、修改基准或确认最终结果。
- 访客数据显式标记为试用数据，不进入正式有效产出/绩效口径；转正式需管理员操作并记录来源，不直接因改角色自动混入历史统计。
- 保留正式编导、主管、运营、投放、负责人、管理员六种角色。若要让访客体验完整闭环，应在隔离试用空间中模拟，不给正式业务确认权。
- 有效期、停用、会话撤销在后端每次敏感请求检查。已有签名URL在有效期内仍可能可用，应采用短TTL；如要求停用后立刻撤回所有视频访问，另需代理鉴权播放方案，不能承诺仅停用JWT即可做到。

### 7.2 配额与费用

上传次数、存储字节、内容评估次数至少独立管理。额度采取原子预占与结算，避免双击/多标签页突破限制。

同一幂等请求不重复扣业务额度；失败是否退还按错误类别和产品政策处理。内部重试可不重复扣访客次数，但真实模型调用可能仍产生费用，两个账本必须分开。每天/月配额按北京时间统一重置边界。

供应商实际账单、余额和云端全量存储容量，只有具备对应只读数据源时才显示。应用持有的最小对象权限不能据此推算整个云账号余额，也不应为了看板给运行账号全量云权限。

## 八、认证、安全与可观测性

- 使用 Secure、HttpOnly、合理 SameSite 的同源会话Cookie；配套CSRF/Origin校验，不能认为Cookie迁移自动解决所有安全问题。
- 服务端管理会话有效性；退出、重置密码、停用和强制下线具有明确失效范围。保留登录限流，合理处理反向代理IP与并发登录。
- 迁移时协调旧 Bearer Token 退出与重新登录，避免新旧认证长期并存形成绕过。
- 视频与报告按对象权限校验；禁止仅凭前端隐藏菜单控制权限。
- 模型及云密钥只在服务端受控环境中管理，不在后台回显或开放任意明文编辑。非敏感配置采用白名单；不提供任意请求地址/远程命令执行入口。
- 不因旧Key“旧”就强制停用；如泄露、权限过大或不再受控，再按已验证的新配置轮换并保留回滚顺序。
- 健康分层：存活检查仅服务进程；就绪检查数据库等必要依赖；管理端展示最近依赖探测；人工端到端诊断明确可能上传测试对象或消耗模型额度。
- 不让普通健康探针每几秒调用一次付费模型。公开健康接口不返回密钥、完整错误栈、内部拓扑或数据库地址。
- 应用记录 requestId、jobId、环节、耗时、错误类别与脱敏供应商请求ID，方便排障。
- 数据库备份、恢复演练、证书续期、磁盘与内存告警作为上线检查项；未接入采集的指标标为未知。

## 九、看板口径与案例管理

业务看板和管理员运行看板分开，避免“内容好”“已评估”“最终有效”被当成同一种成果。

- 业务看板：期间已确认结果、内容/数据等级分布、有效产出、待补数据、人工确认与案例。
- 运行看板：任务数、用户数、成功率、排队/处理耗时、资源错误与费用。
- 期间指标以各自事件时间计数，并在指标说明中写清上传时间/完成时间/确认时间；当前积压单独显示快照时间，不假装随日期变化。
- 分子分母同口径；无样本显示“暂无数据”，不显示误导性0%；重试次数不计为新增视频数。
- 使用 Asia/Shanghai；返修与历史评估的去重规则明确，报表不能直接累加所有AI历史记录。
- 优秀/反面案例来自规定业务结果与人工标记；案例有权限、证据、来源版本、标记人和时间，支持筛选、详情和报告导出。

## 十、数据、接口与改造落点

### 10.1 数据设计

保留12张核心业务表，不重新建一套平行业务结果表。通过增量迁移添加：

- users：访客角色、到期、创建者、首次改密、归档等字段。
- user_sessions：会话与撤销；选择统一撤销机制，避免同时引入多套含义相同的token版本逻辑。
- quota_accounts / quota_ledger：额度账户、预占、扣减、释放、人工调整与幂等键。
- evaluation_jobs / evaluation_job_attempts：持久化任务、租约、重试、输入引用和错误，不替代原评估结果表。
- ai_usage_logs：每次外部调用、可用计费量、价格版本、估算/对账状态。
- service_health_checks：必要的采样与清理策略，不无限保存高频日志。
- system_settings：仅白名单非敏感配置；业务配置复用现有 ai_model_configs / platform_benchmarks 并增加版本审计。
- videos：试用/正式标记、可用文件元数据；评估结果保留模型、Prompt、Schema和基准版本引用。

新增字段先兼容旧读写，再回填；外键/索引/唯一约束与事务设计一并交付。账号归档不破坏历史操作者引用。

### 10.2 接口族（详细DTO在设计阶段冻结）

- `/api/auth/*`：共享登录、身份、改密、退出；管理员入口额外检查管理员权限。
- `/api/admin/users/*`、`/api/admin/roles/*`：账号、授权、到期、会话、额度。
- `/api/evaluation-jobs/:id`：当前用户有权查看的任务状态。
- `/api/admin/evaluation-jobs/*`：全局任务查询、历史、受控恢复和重试。
- `/api/admin/dashboard/*`、`/api/admin/usage/*`：运行指标和用量导出。
- `/api/admin/ai-services/*`、`/api/admin/storage/*`：受控配置状态与诊断。
- `/api/admin/operation-logs/*`、`/api/admin/security/*`、`/api/admin/settings/*`。
- 原视频与评估接口向后兼容；播放URL接口增加过期信息，报告接口逐项校验权限。
- 健康接口保留旧路径的存活语义，新增就绪检查；详细依赖状态仅管理端开放。

## 十二、验收与发布门槛

1. 不刷新页面完成内容评估、数据复盘和最终建议的成功/失败反馈；切后台、回来、换视频、多标签页不串结果。
2. 评估过程中重启API/worker，任务可以恢复或清晰进入可处理状态，不永远running；旧worker不能提交失效结果。
3. 并发点击、断网重试、多个窗口不会重复扣同一业务额度；真实外部重试在调用记录中可追踪。
4. 竖屏、横屏、手机和常见笔记本尺寸均可使用；播放器不挤没下一步操作；过期续签保留进度。
5. 完成真实“上传→内容评估→主管→数据→复盘→规则→最终建议→负责人确认→案例”及返修、数据不足分支。
6. 每个角色执行允许与拒绝用例；访客不能通过猜ID、直接请求、导出或签名接口访问他人数据。
7. 过期/停用/重置密码/退出/撤销会话、登录失败、额度并发均有测试；已有签名的残余有效期有明确说明。
8. 输入更新后不能确认旧来源建议；人工调整必须有理由，所有关键操作有日志。
9. 看板北京时间边界、零样本、试用隔离、重试去重、返修链与人工确认口径用固定样本校验。
10. 模型错误、限流、超时、无效JSON、存储失败、数据库不可用都有可定位的错误和恢复路径。
11. 不向前端、日志或报告泄露密钥；原始模型结果仅受控保留，不直接展示给访客。
12. 先在隔离测试环境进行迁移/恢复演练，备份核验通过；以明确镜像版本发布，保留可回退应用版本。数据库回退不以删表丢数据实现。

当前测试通过只是基线；上述新增场景必须新增验收证据。生产真实模型验收需要单独记录样本、耗时和费用，不能用Mock通过替代。
